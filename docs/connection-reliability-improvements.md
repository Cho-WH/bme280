# micro:bit Web Bluetooth 연결 안정성 검토 및 개선안

## 1. 검토 범위

이 문서는 `firmware/bme280.js` 기반 펌웨어가 올라간 micro:bit와 현재 웹앱이 Web Bluetooth(Nordic UART)로 연결될 때 발생할 수 있는 오류 시나리오를 정리하고, 연결 성공률과 사용자 피드백을 높이기 위한 개선안을 제안한다.

검토한 주요 파일은 다음과 같다.

- `docs/project-overview.md`: 데이터 계약 및 실행 흐름
- `README.md`, `index.html`: 사용자 안내 및 펌웨어 다운로드 안내
- `firmware/bme280.js`: micro:bit MakeCode JS 소스
- `firmware/bme_1.2.hex`: 최신 BME280 펌웨어 HEX 파일
- `js/bluetooth.js`: Web Bluetooth 연결, UART 서비스/특성 탐색, 알림 수신
- `js/ui/connection-panel.js`: 연결 버튼, 오류 메시지, 상태 표시
- `js/utils/parseSample.js`: 수신 데이터 파싱

## 2. 현재 연결 흐름 요약

웹앱의 연결 흐름은 다음 순서로 동작한다.

1. 사용자가 `디바이스 연결` 버튼을 누른다.
2. `navigator.bluetooth.requestDevice()`로 `BBC micro:bit`, `micro:bit`, `BBC microbit` 이름 접두어를 가진 장치를 선택한다.
3. 선택된 장치의 GATT 서버에 연결한다.
4. Nordic UART 서비스 UUID(`6e400001-b5a3-f393-e0a9-e50e24dcca9e`)를 찾는다.
5. 서비스 내부 특성 중 쓰기 가능한 특성을 TX로, 알림 가능한 특성을 RX로 선택한다.
6. RX 알림을 시작한다.
7. 웹앱이 TX 특성에 `bme\n`을 쓴다.
8. 펌웨어가 `bme` 명령을 받으면 100ms마다 `temperature,humidity,pressure\n` 형식으로 데이터를 전송한다.
9. 웹앱은 줄 단위로 데이터를 조립하고, 3필드 CSV로 파싱한 뒤 UI 상태에 반영한다.

현재 구조는 기본 동작에는 충분하지만, 연결은 성공했는데 데이터가 오지 않는 상태를 명확히 구분하지 못한다. 최신 배포 기준은 `bme_1.2.hex`이며, 연결 안정성 개선은 전용 앱/전용 펌웨어 조합을 전제로 웹앱 안내와 재연결 흐름을 중심으로 적용한다.

## 3. 주요 오류 시나리오

### 3.1 브라우저 및 실행 환경 문제

가능한 상황:

- iOS Safari 또는 Web Bluetooth 미지원 브라우저에서 접속한다.
- `file://` 또는 일반 HTTP 주소에서 접속해 Web Bluetooth API가 비활성화된다.
- Android에서 Bluetooth 권한 또는 위치 권한을 거부한다.
- 운영체제 Bluetooth가 꺼져 있거나 브라우저에 Bluetooth 접근 권한이 없다.
- iframe, 앱 내장 브라우저, 제한된 WebView에서 접속한다.

현재 대응:

- `navigator.bluetooth` 존재 여부로 지원 여부를 판단하고 배너/도움말을 표시한다.
- 실제 권한 거부, 사용자 취소, OS Bluetooth 꺼짐 등은 브라우저가 던지는 오류 메시지를 그대로 표시하는 경우가 많다.

리스크:

- 사용자 취소(`NotFoundError`)와 실제 장애가 같은 연결 실패로 보일 수 있다.
- 모바일 권한 문제는 브라우저별 메시지가 달라 사용자가 다음 조치를 알기 어렵다.

### 3.2 장치 선택 및 펌웨어 불일치

가능한 상황:

- 같은 공간에 여러 micro:bit가 있어 사용자가 다른 micro:bit를 선택한다.
- micro:bit에는 Nordic UART가 없는 다른 펌웨어가 올라가 있다.
- `magnetometer.hex` 또는 `v1.1-mg.js` 계열 자기장 펌웨어가 올라가 있다.
- 일부 문서 또는 배포 산출물이 `bme_1.0.hex` 기준으로 남아 있으면 사용자가 구버전 펌웨어를 플래시할 수 있다.
- 최신 `bme_1.2` 펌웨어는 `BME280.humidity()`와 `BME280.pressure(BME280_P.hPa)` API를 사용해 습도/기압의 소수점 측정값 출력을 지원한다.

현재 대응:

- 장치 이름 접두어로 micro:bit 후보를 필터링한다.
- UART 서비스가 없으면 `getPrimaryService()` 단계에서 실패한다.
- 자기장 펌웨어처럼 UART 서비스는 있으나 명령/데이터 형식이 다른 경우, 연결은 성공하지만 유효 데이터가 들어오지 않는다.

리스크:

- 사용자는 연결 상태가 `연결됨`인데 값이 표시되지 않는 상황을 볼 수 있다.
- 잘못된 HEX 파일 안내 때문에 문제 해결이 어려워진다.

### 3.3 GATT 서비스 및 특성 탐색 문제

가능한 상황:

- UART 서비스는 있지만 브라우저가 특성 또는 descriptor 열거를 제한한다.
- 특성 속성 탐색 결과가 브라우저/펌웨어 조합에 따라 다르게 반환된다.
- 동적 탐색에서 쓰기 특성과 알림 특성이 잘못 분류된다.
- `startNotifications()`가 실패하거나, CCCD 설정이 지연된다.

현재 대응:

- 모든 특성을 가져온 뒤 `write/writeWithoutResponse` 속성을 가진 특성을 TX로, `notify/indicate` 또는 CCCD를 가진 특성을 RX로 선택한다.
- 탐색 실패 시 Nordic UART 표준 UUID(`...0002`, `...0003`)로 fallback한다.

리스크:

- 현재 선택 로직은 비교적 유연하지만, 표준 Nordic UART UUID를 우선하지 않는다. 예외적인 특성 구성이 섞이면 잘못된 특성을 먼저 고를 가능성이 있다.
- 특성 탐색 실패 메시지는 사용자에게 기술적으로 보일 수 있다.

### 3.4 명령 전송과 펌웨어 준비 타이밍

가능한 상황:

- GATT 연결 직후 micro:bit가 아직 내부적으로 UART 이벤트를 처리할 준비가 되기 전에 `bme\n` 명령이 전송된다.
- 펌웨어가 연결 전 장치 이름을 반복 표시하는 `while (연결됨 == 0)` 루프를 돌다가 연결 후 모드 전환까지 짧은 지연이 생긴다.
- 연결 직후 첫 명령 write는 성공했지만 펌웨어가 명령을 놓친다.
- 기존처럼 연결 해제 직후 펌웨어가 `control.reset()`으로 재부팅되면, 사용자가 즉시 재연결을 시도할 때 준비 타이밍이 엇갈릴 수 있다.

현재 대응:

- 웹앱은 알림을 먼저 시작한 뒤 `bme\n`을 1회 전송한다.
- 명령 재전송 또는 첫 샘플 수신 확인 로직은 없다.

리스크:

- 연결은 성공했지만 스트리밍이 시작되지 않을 수 있다.
- 사용자가 연결 해제 후 즉시 재연결하면 장치가 스캔 목록에 늦게 나타나거나 GATT 연결이 실패할 수 있다.

### 3.5 데이터 수신 및 파싱 문제

가능한 상황:

- 펌웨어가 `temperature,humidity,pressure`가 아닌 다른 필드 수를 보낸다.
- 센서 초기화 또는 I2C 배선 문제로 값이 `NaN`, 빈 문자열, 비정상 값으로 나온다.
- 라인 조립 중 개행이 누락되거나 매우 긴 버퍼가 쌓인다.
- 자기장 펌웨어는 4필드 데이터를 보내므로 현재 파서는 모든 샘플을 버린다.

현재 대응:

- `parseSample()`은 3개 필드가 아니거나 숫자가 아니면 `null`을 반환한다.
- 파싱 실패는 UI에 노출되지 않는다.

리스크:

- 데이터 포맷 오류, 센서 문제, 잘못된 펌웨어가 모두 “값이 안 보임”으로만 나타난다.
- 파싱 실패가 반복되어도 사용자는 연결 문제인지 센서 문제인지 알 수 없다.

### 3.6 연결 상태 관리 문제

가능한 상황:

- 연결 중 오류가 발생한 뒤 `disconnectDevice()`가 내부적으로 disconnect listener를 호출하고, catch 블록도 상태를 갱신해 상태 변경이 중복된다.
- 수동 연결 해제와 예기치 않은 연결 해제가 거의 동시에 발생한다.
- 연결은 유지되지만 일정 시간 동안 샘플이 들어오지 않는다.

현재 대응:

- GATT disconnect 이벤트에서 상태를 초기화하고 오류 메시지를 표시한다.
- 마지막 업데이트 시간은 샘플 수신 시에만 갱신된다.

리스크:

- “연결됨” 상태와 “데이터 정상 수신 중” 상태가 분리되어 있지 않다.
- 무응답 상태를 자동으로 감지하지 못한다.

## 4. 안정성 개선안

### 4.1 펌웨어/문서 버전 기준 통일

우선순위: 높음

개선 내용:

- 실제 배포할 HEX 파일명은 최신 기준인 `firmware/bme_1.2.hex`로 통일한다.
- README, `index.html`, `docs/project-overview.md`의 펌웨어 파일명과 다운로드 링크를 같은 버전으로 맞춘다.
- 자기장 펌웨어(`magnetometer.hex`, `v1.1-mg.js`)는 BME280 웹앱과 호환되지 않는다는 점을 문서에 분명히 적는다.
- 가능하면 펌웨어 파일명에 데이터 계약을 포함한다. 예: `bme280_uart_3field_10hz_v1.2.hex`.

효과:

- 사용자가 잘못된 펌웨어를 올리는 문제를 줄인다.
- 연결 성공 후 데이터가 안 나오는 문제의 가장 흔한 원인을 줄일 수 있다.

### 4.2 첫 유효 샘플 수신 확인 및 타임아웃 추가

우선순위: 높음

개선 내용:

- `sendBmeCommand()` 이후 일정 시간 안에 첫 유효 샘플이 들어오는지 확인한다.
- 예: 3초 안에 `parseSample()`이 성공하지 않으면 다음 메시지를 표시한다.
  - “micro:bit와 연결됐지만 BME280 데이터가 수신되지 않습니다. 펌웨어가 BME280용인지, 센서 배선이 정상인지 확인하세요.”
- 첫 샘플 전에는 상태를 `connected` 하나로만 보지 말고 `waiting_data`로 분리한다.

권장 상태 모델:

- `disconnected`: 미연결
- `connecting`: GATT 연결 및 서비스 탐색 중
- `waiting_data`: UART 연결 완료, 시작 명령 전송 완료, 첫 샘플 대기 중
- `connected`: 유효 샘플 수신 중

효과:

- “연결은 됐는데 값이 안 뜸”을 실제 진단 가능한 상태로 바꿀 수 있다.

### 4.3 시작 명령 재전송 또는 핸드셰이크 도입

우선순위: 높음

개선 내용:

- 첫 유효 샘플을 받기 전까지 `bme\n` 명령을 짧은 간격으로 제한 횟수 재전송한다.
- 예: 연결 후 300ms 간격으로 최대 5회 전송, 첫 샘플이 들어오면 중단한다.
- 펌웨어 단순성을 유지하기 위해 ACK 기반 핸드셰이크는 이번 적용 범위에서 제외한다.

웹앱 처리:

- 첫 유효 샘플이 들어오기 전까지만 `bme\n`을 제한적으로 재전송한다.
- 첫 샘플 수신, 연결 해제, 타임아웃 중 하나가 발생하면 재전송 루프를 즉시 중단한다.

효과:

- 명령 유실, 잘못된 펌웨어, 센서 데이터 미수신을 구분할 수 있다.

### 4.4 Nordic UART 표준 UUID 우선 선택

우선순위: 중간

개선 내용:

- 특성 선택 시 표준 Nordic UART UUID를 먼저 찾고, 실패할 때만 속성 기반 동적 탐색을 사용한다.
- 표준 매핑:
  - 웹앱이 쓰는 특성: `6e400002-b5a3-f393-e0a9-e50e24dcca9e`
  - 웹앱이 알림을 받는 특성: `6e400003-b5a3-f393-e0a9-e50e24dcca9e`
- 현재 fallback으로만 쓰는 UUID 매칭을 우선 로직으로 올리는 것이 좋다.

효과:

- 예외적인 descriptor/속성 반환 차이에도 표준 UART 펌웨어와 안정적으로 연결된다.

### 4.5 파싱 실패 진단 추가

우선순위: 중간

개선 내용:

- `parseSample()`이 실패한 원인을 구분한다.
  - 필드 수 불일치
  - 숫자 변환 실패
  - 빈 라인
  - 범위 밖 값
- 최근 파싱 실패 횟수와 마지막 원본 라인을 개발자용 상태 또는 콘솔에 남긴다.
- 첫 샘플 대기 중 파싱 실패가 반복되면 사용자 메시지를 표시한다.

예시 메시지:

- 4필드 수신: “현재 micro:bit가 BME280 형식이 아닌 4개 필드 데이터를 보내고 있습니다. 자기장 펌웨어가 올라가 있지 않은지 확인하세요.”
- 숫자 변환 실패: “센서 값이 숫자로 수신되지 않았습니다. BME280 배선 또는 센서 초기화를 확인하세요.”

효과:

- 잘못된 펌웨어와 센서 문제를 빠르게 구분할 수 있다.

### 4.6 샘플 수신 감시(stale watchdog) 추가

이번 적용 범위에서는 제외하고 후순위로 둔다.

우선순위: 중간

개선 내용:

- `lastUpdatedAt` 기준으로 일정 시간 이상 샘플이 없으면 `stale` 상태를 표시한다.
- 100ms 샘플링 기준으로 2~3초 이상 무수신이면 경고를 표시한다.
- 연결 자체가 끊기지 않았더라도 “데이터 수신 중단”을 사용자에게 알려준다.

권장 기준:

- 첫 샘플 대기 타임아웃: 3초
- 스트리밍 중 무수신 경고: 2초
- 재시작 안내 표시: 5초 이상 무수신

효과:

- BLE 연결은 살아 있으나 펌웨어 모드가 멈췄거나 센서 루프가 중단된 상황을 감지할 수 있다.

### 4.7 오류 메시지 매핑 개선

우선순위: 중간

개선 내용:

- 브라우저 오류 이름별로 사용자 친화적 메시지를 제공한다.

권장 매핑:

| 오류 이름/상황 | 사용자 메시지 |
| --- | --- |
| `NotFoundError` | “장치 선택이 취소되었거나 조건에 맞는 micro:bit를 찾지 못했습니다.” |
| `NotAllowedError` | “Bluetooth 권한이 거부되었습니다. 브라우저/운영체제 권한을 허용해 주세요.” |
| `NetworkError` | “Bluetooth 연결이 중간에 끊겼습니다. micro:bit 전원과 거리, 다른 연결 여부를 확인하세요.” |
| `SecurityError` | “Web Bluetooth는 HTTPS 또는 localhost에서만 사용할 수 있습니다.” |
| UART 서비스 없음 | “선택한 micro:bit에 BME280 UART 펌웨어가 올라가 있지 않은 것 같습니다.” |
| 첫 샘플 없음 | “연결은 됐지만 BME280 데이터가 수신되지 않습니다. 펌웨어와 센서 배선을 확인하세요.” |

효과:

- 사용자가 다음 조치를 바로 알 수 있다.

### 4.8 재연결 흐름 보강

우선순위: 낮음~중간

개선 내용:

- 연결 해제 직후 웹앱의 GATT/notification 정리와 micro:bit BLE 상태 정리가 겹치지 않도록 짧은 대기 시간을 둔다.
- 수동 연결 해제 후 2초 동안 “micro:bit 연결을 정리하는 중입니다. 잠시 후 다시 연결하세요.” 안내를 표시하고 연결 버튼을 잠시 비활성화한다.
- 예기치 않은 연결 해제 시에는 “다시 연결” 버튼을 바로 제공하되, 실패하면 재시도 간격을 둔다.

효과:

- 사용자가 너무 빠르게 재연결을 시도해 실패하는 상황을 줄인다.

### 4.9 펌웨어 측 개선

우선순위: 중간

개선 내용:

- 연결 해제 시 `control.reset()`으로 전체 재부팅하지 않고, `연결됨`, `modes`, `inputs`만 초기화한다.
- ACK/ERROR 같은 추가 프로토콜은 펌웨어를 단순하게 유지하기 위해 넣지 않는다.
- UART 서비스는 최초 `Setup()`에서 시작한 상태를 유지하고, 다음 연결에서 웹앱의 `bme\n` 명령을 다시 받도록 한다.

효과:

- 연결 해제 후 micro:bit 재부팅 시간을 없애 재연결 실패 가능성을 줄인다.

## 5. 권장 구현 순서

1. README, `index.html`, `docs/project-overview.md`의 펌웨어 버전 표기를 `bme_1.2.hex`로 통일한다.
2. `connection-panel.js`에 `waiting_data` 상태, 첫 유효 샘플 타임아웃, 사용자 친화적 오류 메시지 매핑을 추가한다.
3. 첫 샘플 전 `bme\n` 명령을 제한 횟수 재전송한다.
4. 수동 연결 해제 후 2초 동안 연결 버튼을 비활성화해 즉시 재연결 시도를 막는다.
5. 펌웨어의 disconnect 처리에서 `control.reset()`을 제거하고 상태 변수만 초기화한다.

## 6. 검증 체크리스트

### 정상 연결

- BME280 펌웨어가 올라간 micro:bit를 선택하면 3초 안에 첫 샘플이 표시된다.
- 연결 상태가 `연결 중`에서 `데이터 수신 중`으로 바뀐다.
- 10Hz 기준으로 차트와 로그가 계속 갱신된다.

### 잘못된 펌웨어

- 자기장 펌웨어가 올라간 micro:bit를 선택했을 때 연결 성공 후 무응답으로 방치되지 않는다.
- 첫 샘플 타임아웃 후 `bme_1.2.hex` 펌웨어와 BME280 센서 배선을 확인하라는 안내가 표시된다.

### 센서 문제

- BME280 배선이 빠진 상태에서 연결했을 때 센서 문제 안내가 표시된다.
- 숫자가 아닌 값 또는 비정상 값만 들어오면 첫 샘플 타임아웃 안내가 표시된다.

### 브라우저/권한 문제

- Web Bluetooth 미지원 브라우저에서 연결 버튼이 비활성화되고 지원 브라우저 안내가 표시된다.
- 장치 선택 취소와 실제 연결 실패가 서로 다른 메시지로 표시된다.
- HTTPS가 아닌 일반 배포 주소에서는 보안 컨텍스트 안내가 표시된다.

### 재연결

- 연결 해제 직후 재연결 시도에서 micro:bit 재부팅 대기 안내가 표시된다.
- micro:bit 전원을 끄면 GATT disconnect 이벤트가 처리되고 UI가 `연결 안 됨`으로 돌아간다.
- 다시 전원을 켠 뒤 재연결하면 첫 샘플 대기 및 스트리밍 상태가 정상 갱신된다.

## 7. 결론

현재 웹앱은 Nordic UART 연결과 3필드 CSV 수신이라는 기본 경로는 구현되어 있다. 전용 앱/전용 펌웨어 조합에서는 복잡한 핸드셰이크보다 “GATT 연결 성공”과 “BME280 데이터 스트리밍 성공”을 UI 상태로 분리하고, 연결 해제 직후 재연결 타이밍을 안정화하는 것이 우선이다.

가장 먼저 처리할 개선은 다음 3가지다.

1. 연결 후 첫 유효 샘플 타임아웃과 사용자 메시지를 추가한다.
2. `bme\n` 시작 명령을 첫 샘플 수신 전까지 제한적으로 재전송한다.
3. 연결 해제 시 펌웨어 재부팅을 피하고, 웹앱은 짧은 재연결 대기 시간을 둔다.

이 세 가지를 적용하면 사용자가 가장 자주 겪는 “연결은 됐는데 값이 안 보이는 문제”를 명확하게 진단하고 복구할 수 있다.
